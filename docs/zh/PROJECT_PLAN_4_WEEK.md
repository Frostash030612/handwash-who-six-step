## 0. 计分规则（先看这一节）

### 0.1 分数在哪里

| 考核项 | 权重 |
| --- | --- |
| Practice Module 项目作品（文档 + MVP 交付物） | 50% |
| 笔试（3 小时，开卷） | 50% |
| **总分 50% 及格** | |

项目作品这 50% 的拆分 —— **这就是本计划的骨架**：

| 计分项 | 权重 | 完成周 | 内容 |
| --- | --- | --- | --- |
| 首次展示 First Presentation | 5% | 第 1 周 | 目标、数据资源、技术/工具、进展 |
| 最终展示 Final Presentation | 10% | 第 4 周 | 10–15 分钟录制视频 |
| 最终报告 Final Report | 15% | 第 4 周 | 工具/技术、系统设计、系统性能、发现与讨论 |

### 0.2 官方硬性要求

1. 团队**最多 5 人** —— 你们 4 人，符合。
2. 项目必须**开发、集成并演示以下 4 项能力中的至少 3 项**：

   | 编号 | 能力 | 本项目如何满足 |
   | --- | --- | --- |
   | A1 | 有监督 / 无监督学习 | **有监督**：帧级六分类；以视频为单位的训练/验证/测试划分 |
   | A2 | 机器学习 / 深度学习技术 | **深度学习**：YOLO26n-cls + MobileNetV2（迁移学习） |
   | A3 | 混合机器学习 / 集成方法 | **混合 + 集成**：帧级模型 × 时序模型（GRU/TCN），用概率平滑与多数投票融合 |
   | A4 | 智能感知 / 意义建构 | **意义建构**：把视频当作传感器流；时序分段把逐帧标签变成动作序列与规范性判定 |

   **按 4 项准备，保底 3 项。** A4 是最容易在截止压力下被砍掉的一项，
   所以它有独立负责人（见第 2 节），而且它的交付物就是演示 —— 反正最终视频也需要它。
3. 交付物：可运行系统、数据集、最终报告、**10–15 分钟**视频演示、两次汇报的 PPT、代码与模型文件。
4. **附加提交**：每位成员 **1–2 页个人报告**（个人贡献；学到的最有用的东西；如何应用到别的场景）
   + 通过系统提交同伴互评。
5. 提交方式：2026 年 10 月 31 日，Canvas → Assignments → Practice Module。
   **每队只交一个 ZIP**，个人报告单独提交。

## 1. 团队协作铁律（不可协商）

这些规则的存在，是为了让 4 个人并行工作而不互相破坏。

| 规则 | 原因 | 由什么强制执行 |
| --- | --- | --- |
| 所有改动走 Pull Request | 两人同时改一个文件 = 丢工作 | `CONTRIBUTING.md` 第 5 节 |
| 未经 RFC 不许动 `src/handwash/core/` | 这是契约层；改了会让所有人的结果失效 | `CODEOWNERS`、`scripts/check_structure.py` |
| 数据按**原始视频**划分，绝不按帧 | 帧级随机划分会泄漏数据、虚高准确率 | `io/split.py` 的三道校验 |
| 每次实验记录 `config_hash` | 否则结果之间不可比 | `docs/EXPERIMENTS.md` |
| 每个 PR 前跑 `make check` | CI 与本地必须一致 | `Makefile`、`.github/workflows/ci.yml` |

**会议节奏**：每周一 30 分钟同步（定本周计划、认领 PR）；每周四 15 分钟对齐（解阻塞）。
决策一律写进 `docs/EXPERIMENTS.md` —— **没写下来就等于没发生**。

## 2. 四个角色（一条工作线一个负责人，不搞共同负责）

共同负责 = 没人负责。每条工作线只有一个 owner，其他人只做 review。

| 角色 | 成员（填名字） | 负责 | 主要模块 / 文件 | 服务于哪个计分项 |
| --- | --- | --- | --- | --- |
| **R1 — 数据与评估负责人** | | 数据集、划分、指标、评估协议、统计结论 | `src/handwash/io/`、`src/handwash/data/`、`scripts/prepare_data.py`、`docs/DATA.md`、`docs/EXPERIMENTS.md` | 最终系统、最终报告（性能） |
| **R2 — 模型与训练负责人** | | 帧级分类器、训练流程、基线、超参 | `src/handwash/models/`、`src/handwash/pipelines/train.py`、`configs/models/`、`configs/experiments/` | 最终系统、最终报告（设计） |
| **R3 — 时序与判定负责人** | | 时序融合、完整性规则、跨场景鲁棒性 | `src/handwash/models/temporal.py`、`src/handwash/core/protocol.py`、`configs/config.yaml` 的 `assess` 段 | 最终系统（本项目的差异点） |
| **R4 — 产品、演示与交付负责人** | | 可运行 demo、视频、PPT、报告整合、ZIP、互评事务 | `scripts/run_assess.py`、`docs/REPORT_OUTLINE.md`、`deliverables/` | 首次展示、最终展示、最终报告、同伴互评 |

**为什么这样分**：R1 与 R2 第一天就能互相解锁（划分 → 第一条基线）。
R3 依赖 R2 的 checkpoint，但第 1 周就可以用合成数据把时序头写完并单测。
R4 承担最早的截止（9/30 展示）与最晚的截止（10/31 ZIP），
所以"演示负责人"必须同时是"交付负责人"—— 责任集中到一个人身上才追得动。

**负载检查**：每个角色约 2.5 天/周。任何角色某周超过 4 天，就是计划出了问题，
在周一同步会上提出来。

### 第 3 周 —— 做出差异点：时序消融、完整性评估、鲁棒性

**目标**：产出能回答研究问题的证据。这一周把"我们训了个分类器"变成
